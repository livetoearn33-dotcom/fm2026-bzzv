# 幕聊介面精修說明 v0.3

改動對象：`幕聊 v2 Raycast.dc.html`（原始檔沒有動）
產出：`refined.html`（純 HTML / CSS / vanilla JS，瀏覽器直接開，也能塞進 WebView）
日期：2026-09-01

---

## 先講三句話

1. **這個系統本來就不差，問題不是缺東西，是東西太多。** 我拿掉的比加上的多很多。
2. **最傷的不是美感問題，是可信度問題。** 卡片上有 `esc`、`⌘C`、`⌘R`、`⇥` 這些桌機鍵盤提示——Android 上沒有這些鍵。台下坐著五個工程背景的評審，這個細節會被看到。
3. **形態改成鍵盤之後，有些原本的答案要反過來。** 一張四邊自由的卡片和一條貼邊的面板，是不同的排版問題。下面有一節專門講這個。

## 名詞先解釋（後面會一直用到）

| 詞 | 白話意思 |
|---|---|
| **hairline（髮絲線）** | 1px 的細線，用來分隔區塊 |
| **inset shadow（內陰影）** | 陰影畫在元件「裡面」，看起來像被壓下去，不像浮在上面 |
| **drop-shadow（外陰影）** | 陰影畫在元件外面，看起來浮起來。Raycast 明文禁止，我們也沒用 |
| **表面色階** | 用「底色深淺不同」來分層，取代畫線。例如 `#07080a` 上面疊一塊 `#111214` |
| **ellipsis（省略號）** | 文字太長時結尾變成「…」 |
| **tap target（點擊區）** | 手指可以按到的範圍。Android 建議至少 48dp，44dp 是可接受下限 |
| **eyebrow（眉標）** | 標題上方那行很小的說明字，像眉毛在眼睛上面 |

## 二、形態改變：從浮層卡片 → 鍵盤面板

（這是收到「懸浮球和浮層卡片不在團隊共識裡」之後重做的部分。）

原本卡片裡的內容區塊，現在長在鍵盤上方的面板裡。**大部分減法判斷照搬，但有三個判斷因為容器改變而反過來**，這三個值得說清楚：

### 反轉 1：內凹容器 → 拿掉

- **卡片版做法**：回覆文字放進 `#111214` 的內凹框，讓「要送出的那句話」變成一個看得見的物件。
- **面板版做法**：拿掉那個框，17px 白字直接放在面板底色上。
- **為什麼反過來**：卡片版的回覆旁邊還有六個同寬、同左緣的區塊，不裝進框裡就沉沒。面板版的收合列（`#07080a`）和展開面板（`#111214`）本身就是兩層不同底色，展開面板整塊已經是一個容器了。**在容器裡再放一個容器，就是糊。**

### 反轉 2：來源標籤（chip）→ 留下；依據抽屜 → 拿掉

- **卡片版做法**：把 `#Q-2410`／`交期 14 天` 這排小標籤刪掉，保留可展開的「引用依據」表格（來源 → 實際數值）。
- **面板版做法**：完全相反——保留小標籤，砍掉依據表格。
- **為什麼反過來**：卡片有四邊，塞得下一個 key→value 表格。鍵盤面板的高度被鍵盤壓著，而且「收合 → 展開 → 再展開依據」是三層，沒有人在手機鍵盤上點三層。標籤本來就寫成 `#P-118 · 14 天` 這種「編號 · 數值」格式，等於把表格壓成一行。
- **代價**：`#Q-2410` 完整的價格內容（A 規格 NT$248／pcs…）現在看不到了。這是我主動放棄的資訊，Zeno 可以否決。

### 反轉 3：3dp 風險色帶 → 拿掉

- 元件貼紙表裡有一條「W 3dp、全高、卡片最左緣」的風險色帶。
- 卡片版我留著（卡片有邊，色帶貼在邊上有意義）。
- **面板版拿掉**：面板是貼齊螢幕左右緣的，3px 色條貼在螢幕最左邊，看起來像螢幕壞掉，不像設計。語氣改由收合列裡的 mood chip（`高壓`／`敏感`）單獨承擔。

### 其他跟著容器變的數值

| 項目 | 卡片版 | 面板版 |
|---|---|---|
| 左右外邊距 | 12px（四邊都有） | 0（貼齊螢幕左右緣） |
| 圓角 | 16px 四角 | `16px 16px 0 0`（只有上面兩角） |
| 外框 keyline | 四邊 1px `rgba(255,255,255,.25)` | 只有上緣一道 1px inset 亮線 |
| 定位 | `position:absolute; bottom:12px` | 一般文件流，直接接在鍵盤上面 |
| scrim（半透明遮罩） | 有，`rgba(4,5,6,.48)` | **拿掉**。輸入法不會遮住宿主 App |

## 三、逐項改動（含改前 → 改後數值）

### A. 分隔線：5 條 → 0 條

原檔卡片內有四條 `1px solid #1b1c1e`（品牌列下、策略帶下、依據面板上、動作列上），建議條再一條，共五條。

- **改後**：面板內部 **0 條**。分層全部改用表面色階：收合列 `#07080a` → 展開面板 `#111214`。
- 面板唯一的線是上緣那道 `rgba(255,255,255,0.25) 0 1px 0 inset`——那條原本就有，是它跟鍵盤的分界。

### B. 動作：4 個 → 1 個

原檔動作列：`送出 ⏎`、`複製 ⌘C`、`換一版 ⌘R`、`看依據`。

| 元素 | 處置 |
|---|---|
| 送出 | 改名 **填入**，唯一的 Mist 填色按鈕 |
| 複製 | **刪除**。手機上「複製」是桌機腦的選項，demo 時不會有人按 |
| 換一版 | 降級成展開面板右下角的 10px mono 文字鍵 |
| 看依據 | **刪除**（依據抽屜整個拿掉，見反轉 2） |

**「送出」改「填入」的理由不只是減法，是誠實**：Android 輸入法只能把字塞進輸入框，**沒有權限替使用者按送出**。原本寫「送出」，被工程背景的評審問一句就破功。改成「填入」之後，「送不送是你按的」變成產品的信任賣點，而不是要圓的謊。

### C. 字級：6 種 → 4 種

主對話診斷說「字級只有四種」——**這條是錯的**。我實際數過原檔幕聊介面上的字級：

| 字級 | 原檔用在哪 |
|---|---|
| 17px / 400 | 卡片回覆本文 |
| **15px / 400** | 建議條展開後的建議句 ← 第五種 |
| 13px / 500 | 建議條主標、按鈕 |
| 12px / 400 | 策略說明、理由行 |
| **11px / 400** | 建議條的理由行 ← 第六種 |
| 10px mono | 微標籤、快捷鍵 |

- **15px → 17px**：建議條的建議句和卡片的回覆本文**是同一件東西**（一句可以直接用的話），本來就不該有兩種字級。順帶好處：17px 在投影機上明顯好讀。
- **11px → 12px**：理由行統一。
- 改後：**17 / 13 / 12 / 10，四種**。

（手機裡 LINE 那一側的 14px／13px／11px 不算——那是宿主 App，刻意是另一套系統。）

### D. 垂直節奏：6 種內距 → 2 個數字

原檔卡片各區塊的內距是：`12px 16px`、`8px 16px`、`16px`、`0 16px 12px`、`0 16px 12px`、`12px 16px`、`8px`——**七個區塊六種不同的垂直內距**。

這是「業餘感」最直接的來源：眼睛掃過去每一格的呼吸都不一樣，就會覺得歪，但說不出哪裡歪。

- **改後**：展開面板 `padding: 16px` 四邊統一，區塊之間 `gap: 8px`。**只有 16 和 8 兩個數字。**

### E. 對齊：拿掉 `align-items: baseline`

原檔策略帶用 `align-items: baseline` 把 10px mono 的標籤和 12px 兩行的說明擺同一行。

主對話診斷說這是「對不齊」——**症狀對，但改 `align-items` 治不好**。真正的問題是：一個 10px 全大寫的 mono 標籤，跟一段會換行的 12px 內文，本來就不該共用一行。baseline 對齊在第二行出現的瞬間必然崩掉。

- **改後**：`高壓` 變成收合列眉標行裡的一顆 chip（和 `◆ 幕聊` 同一行，都是單行元素，不會換行），情境判讀變成收合列第二行，各佔一行，**結構上不可能對不齊**。
- 唯一還在用的軸線對齊是展開面板底部 `.footrow` 的 `align-items: flex-end`——讓「換一版」落在理由行**最後一行**的高度。理由換幾行都不會撞到它。

### F. 灰色小字：3 層 → 1 層

原檔有三層灰：策略說明 `#9c9c9d`、理由行 `#6a6b6c`、標籤列。堆在一起就是「灰泥感」。

我第一版改完之後回頭看，發現**我自己又做出了同樣的問題**：展開面板裡「情境判讀」和「理由行」都是 12px 灰字，一上一下夾著 17px 本文。兩句都在講「為什麼」：

- 情境判讀 = 為什麼這個情境要這樣回
- 理由行 = 為什麼這樣寫有效

在一條被鍵盤壓著的面板裡，**一句「為什麼」就夠**。所以：

- **情境判讀移到收合列第二行**（不佔展開面板的高度，而且收合時就看得到，是最該被看到的一行）
- **展開面板只留理由行一條灰字**
- 面板高度因此從 297dp → **271dp**，對話區從 109dp → **135dp**，兩顆訊息泡泡不再被切到

### G. tap target：33dp → 40dp

元件貼紙表寫「按鈕 H 33dp」。Android 的建議最小點擊區是 48dp，44dp 是可接受下限，**33dp 太小**。

- 主要動作按鈕：`padding: 8px 12px`（實高 33dp）→ **固定 `height: 40px`**
- chevron（展開箭頭）：`padding: 9px 10px` 的有邊框方塊 → **32×40px 無邊框**，而且**整塊文字都變成展開觸發區**（真實的可展開列都是這樣，箭頭只是指示，不是唯一入口）

### H. 收合列寬度：把 20px 讓給標題

`他已經問第二次 · 這時候他要的是有人接住` 這行是產品的差異點，被 ellipsis 切掉很可惜。

- 收合列 `gap: 12px → 8px`（省 8px）
- chevron 寬 `40px → 32px`（省 8px）
- 按鈕左右內距 `14px → 14px`（沒動）
- 合計標題多拿到約 20px

### I. 對話區靠底對齊 —— 這條主對話沒診斷到，但它是最大的一個

原檔的對話區是 `flex-direction: column` 沒有指定 `justify-content`，所以訊息**貼在對話區的最上面**。

**真實的聊天室，最新訊息永遠貼著輸入框。** 沒有任何一個 App 是把訊息推到頂端、下面留一片空白的。

主對話的診斷第 5 條說「對話區大量留白 → 重心不穩」——那是症狀。**病因是這一個 CSS 屬性沒寫。** 它也是整份稿子裡最像「做的人沒有打開 LINE 看過」的地方。

- **改後**：`justify-content: flex-end`。空白跑到上面去（那才是對的，上面本來就是還沒捲到的舊訊息）。

### J. 輸入框內的中文斷行 bug

原檔輸入框是 `display:flex; flex-wrap:wrap`。flex 會把每個 `<span>` 和文字節點**當成獨立的 flex item**，所以語氣標記結束後的那個「，」被丟到下一行開頭：

```
這個交其本來就不是我能決定的
，你要問生產那邊          ← 逗號開頭，中文排版錯誤
```

- **改後**：打字狀態改 `display: block` + `line-break: strict`。

### K. 語氣底色：8% → 14%

輸入框裡語氣段落的底色是 `rgba(69,35,36,0.08)`。`#452324` 是深棕色，8% 疊在淺灰 `#f2f2f3` 上幾乎等於沒有——投影機上一定看不到。

- **改後**：`0.08 → 0.14`。（仍然偏弱，見第六節。）

### L. Mist 白色填色：收攏成一個意思

這是配合新的「附加」按鈕做的判斷。

Raycast 的規矩是「主要動作一律 Mist `#e6e6e6` 填色，系統裡沒有彩色 CTA」。但如果待命狀態的「附加」也是白色填色，那條 bar 在使用者打字的**全程**都掛著一顆亮白按鈕，很吵，而且白色就失去意義了。

- **待命的「附加」用次要樣式**：透明底 + 1px `#363739` 邊框 + `#9c9c9d` 文字。它是邀請，不是建議。
- **Mist 填色只在「有建議」「展開」「防自爆」出現**。

於是白色填色有了一個明確的意思：**幕聊手上真的有東西給你。** 這跟 Raycast 把珊瑚紅限制在品牌標記是同一種節制。

### M. 讀取中：不做 spinner

「要讓人感覺到它剛剛看了一眼，但不要佔滿畫面。」

- 面板上緣**本來就有**一道 1px 的 inset 亮線（那是它跟鍵盤的分界）。讀取中就沿著那條線掃一道光：`linear-gradient(90deg, transparent, rgba(255,255,255,.75), transparent)`，寬度 35%，`1100ms linear infinite`。
- 加一個 10px mono 的「讀取中」在菱形旁邊。
- **沒有 spinner、沒有進度條、沒有遮罩、菱形不閃不跳。** 用一個已經存在的元素做狀態，不新增元素。

### N. 採用後：差別在輸入框，不在條上

採用後那條 bar 就回到待命（菱形 + 附加）——建議已經被用掉了，條上沒有東西好顯示。我沒有做「已填入」的確認提示，因為那是加法。

差別做在別的地方：

- 輸入框裝進填入的文字（`#9c9c9d` placeholder → `#1b1c1e` 實字）
- **送出鍵這時才變色**（`#f2f2f3` → `#1b1c1e`）

「幕聊只把字放進去，送出鍵活起來、等你按」——這一格畫面本身就是信任故事，不用寫字解釋。

### O. 轉場

| 動作 | 數值 |
|---|---|
| 面板展開／收合 | `grid-template-rows 200ms cubic-bezier(0.16, 1, 0.3, 1)` |
| 本文換版淡入 | `180ms` 同一條曲線 |
| 按鈕 hover | `150ms` |
| 讀取中掃光 | `1100ms linear infinite`（這是持續動畫不是轉場，不受 150–250ms 限制） |

曲線是 expo-out，**沒有回彈、沒有 overshoot**，符合「不要彈跳動效」。

## 四、我拿掉了什麼（這節最重要）

按「拿掉的代價由大到小」排：

| # | 拿掉的東西 | 為什麼 |
|---|---|---|
| 1 | **`esc` 標籤、`⌘C`、`⌘R`、`⇥` 四個桌機鍵盤提示** | **Android 上沒有這些鍵。** 這不是美感問題是可信度問題，而且評審裡有三個工程師。這是我拿掉的最重要的東西。 |
| 2 | **「引用依據」抽屜 + 看依據按鈕** | 資訊跟標籤列重複，而且在鍵盤上是第三層展開。代價：完整的價格數值看不到了，這條 Zeno 可以否決 |
| 3 | **「複製」按鈕** | 手機上沒人用，demo 時不會按。Grammarly / Vercel / Linear 都只有兩個動作 |
| 4 | **五條 1px 分隔線** | 改用表面色階。Linear 的 agent 面板、Grammarly 的建議卡、Superhuman 的助理卡，內部分隔線都是零 |
| 5 | **標籤列的「觀察類」標籤**（催問 ×2、敏感詞 · 降價 這些的重複部分） | 它們和情境判讀在講同一件事。`他已經問第二次` = `催問 ×2`；`話題已碰到價格` = `敏感詞 · 降價`。**標籤列裡沒有一項是原創資訊**：一半重複情境判讀（觀察），一半重複依據抽屜（來源）。鍵盤版留下標籤、砍掉抽屜，是選了比較省高度的那一半 |
| 6 | **`↳` 箭頭符號**（出現兩次） | 一個 mono 字元在做「換行」就能做的事，而且它是 baseline 對齊出問題的來源 |

## 五、我不同意主對話診斷的地方

診斷有六條，我同意四條、修正兩條、補三條沒被看到的。

### ❌ 不同意 1：「字級只有四種」

實際是**六種**。多出來的 15px（建議條建議句）和 11px（建議條理由行）就藏在建議條裡。已修正為四種。

### ❌ 不同意 2：「對話區大量留白 → 重心不穩」

留白是**症狀**，不是病。病因是對話區沒有 `justify-content: flex-end`，訊息被釘在頂端——真實聊天室不是這樣的。修好這一個屬性，留白自動跑到上面（那才是它該在的地方）。

我認為這是整份稿子裡最像「沒打開 LINE 看過」的一處，比 `top: 216px` 嚴重得多。

### ⚠️ 修正 1：「策略帶 baseline 對不齊」

症狀對，開的藥不對。改 `align-items` 沒用——只要 12px 那段有第二行，baseline 就一定崩。要改的是**不要讓一個單行標籤和一段會換行的內文共用一行**。

### ⚠️ 修正 2：「問題在資訊層級太多層」

方向對，但講得不夠準。七個區塊本身不是問題，Linear 的面板也有五六塊。真正的問題是：

**七個區塊全部同寬、同左緣、同一種處理方式，所以 17px 這個字級在單獨扛全部的層級關係。**

真實產品的做法是讓「要送出的那句話」在**視覺上是一個物件**（Grammarly 和 Linear 都把它放進一個底色不同的框），其他東西是繞著它的註解。層級要靠「不同種類的處理」建立，不是靠「同一種處理排七次」。

### ➕ 補充 1：桌機鍵盤提示（最傷的一條，兩邊都沒列到）

見第四節第 1 項。

### ➕ 補充 2：標籤列裡沒有原創資訊

見第四節第 5 項。這是唯一一個「刪掉之後什麼都沒少」的區塊。

### ➕ 補充 3：`#363739` 不是 Raycast 的 token

Raycast 的深色按鈕邊框是 Slate `#2f3031`，token 表裡沒有 `#363739`。

**但我決定不改。** 理由：`#2f3031` 疊在 `#07080a` 上對比極低，在會議室投影機上（對比通常比螢幕差一大截）ghost 按鈕的邊框會直接消失。`#363739` 是這套系統自己那條六階色梯的第五階，內部自洽。**這是刻意的偏離，不是漏改。**

（順帶：主對話說「卡片內距 16px」——Raycast 的規範是 24px。但那是 1200px 寬的桌機行銷頁；374px 寬的手機面板照抄 24px 只會把文字擠掉。我留 16px，這也是刻意偏離。）

## 六、還沒解決的問題

1. **情境判讀還是會被切掉約 2 個字。** `他已經問第二次 · 這時候他要的是有人接住`（20 字）在 56dp 收合列裡放不下，顯示到「…是有人…」。我已經榨出 20px 給它了。**再要救就得改文案**（例如砍成 `他已經問第二次 · 他要的是有人接住`，16 字剛好），但文案不是我的守備範圍，交給 Zeno 決定。

2. **語氣底色在投影機上還是偏弱。** 從 8% 提到 14% 了，但 `#452324` 是低彩度深棕，疊在淺灰輸入框上就是不搶眼。目前真正在承擔標記工作的是那條 2px 實線底線。要更明顯就得換一個專門給淺色底用的暖色，那會動到 token，我沒有擅自改。

3. **字型是從 Google Fonts 線上載的。** 上台前要把 Noto Sans TC 和 JetBrains Mono **自己包進 App**，不然現場網路一斷，字型 fallback 整個畫面就走樣。這是 demo 當天的實際風險，優先度不低。

4. **「讀取中」沒有失敗狀態。** 如果截圖讀不到、或 AI 回不出東西，那條 bar 要顯示什麼？現在沒設計。Demo 走 happy path 沒事，但被評審亂點可能卡在讀取中。

5. **`高壓 #452324` 和 `敏感 #4a3a1f` 在投影機上會很像。** 兩個都是低彩度深色，一個偏紅一個偏黃，差異在會議室投影下大概率分不出來。文字標籤（`高壓`／`敏感`）救得回來，但顏色這一層等於失效。

6. **防自爆沒有做待命狀態。** 這是刻意的——防自爆讀的是你自己打的字，輸入法本來就看得到，不需要「附加」。但也代表 deck 2 的手機永遠停在「已經有建議」的畫面。如果要展示「沒風險時整條不存在」，得再加一格。
